# Database Schema

MySQL, plain parameterized SQL via `mysql2` (no ORM). Schema lives in
`backend/database/migrations/*.sql`, applied in order by `backend/database/migrate.js`
(idempotent — tracks applied files in a `_migrations` table, safe to re-run).

- `001_init.sql` — phase 1: users, departments, wards, complaints, complaint_images,
  complaint_status_history, complaint_embeddings, incidents, incident_complaints, feedback,
  notifications.
- `002_intelligence.sql` — phase 2: AI-enrichment columns on `complaints`, plus
  `incident_events`, `sla_escalations`, `complaint_reopenings`, `ai_situation_reports`,
  `ai_admin_queries`. Also widens `complaint_images.image_type` to include `REOPEN`.

## Indexes

Beyond primary/foreign keys, explicit indexes exist on: `complaints.category`,
`.status`, `.priority_level`, `.department_id`, `.ward_id`, `.created_at`, `.incident_id`,
`.user_id`, `(latitude, longitude)`; `incidents.status`, `.category`, `(latitude,
longitude)`; `complaint_images.complaint_id`; `complaint_status_history.complaint_id`;
`notifications.(user_id, is_read)`; `incident_events.incident_id`;
`sla_escalations.complaint_id`, `.to_sla_status`; `complaint_reopenings.complaint_id`;
`ai_situation_reports.created_at`; `ai_admin_queries.created_at`.

## Notable constraints & design choices

- **Embeddings as JSON text, not a vector DB.** `complaint_embeddings.embedding` is a
  `LONGTEXT` holding a JSON float array; cosine similarity is computed in Node
  (`utils/vectorMath.js`). Practical at this scale, avoids standing up a separate service.
- **`severity_signals`, `evidence_analysis`, `priority_reasons`, `missing_information`,
  `ai_officer_checklist`, `resolution_verification` are all `JSON` columns** — AI-derived or
  computed structured data that doesn't need its own relational shape. `near_school`/
  `near_hospital` admin-search filters read `severity_signals` via `JSON_EXTRACT` rather
  than needing a separate schools/POI table.
- **`ai_admin_queries.filters_json` stores the *sanitized, applied* filter object, not the
  AI's raw output** — this table is the audit trail for what actually ran against the
  database, which is the security-relevant thing to log.
- **`incident_events.event_type` is a free-text varchar, not an enum** — new event types
  (e.g. future workflow steps) don't require a migration.
- **Demo/seed data is distinguishable**, not separately tabled: `wards.is_demo` flags demo
  ward rows, and seeded complaints/incidents use `complaint_number`/`incident_number`
  prefixes (`CMP-SEED-...`, `INC-SEED-...`) distinct from live `CMP-YYYY-NNNNN` /
  `INC-YYYY-NNNN` numbers, so a query or a human can always tell them apart.

## Seed data

- `npm run seed` — departments, demo wards (`(DEMO)` labeled), 1 admin, 1 officer per
  department, 15 citizens. All demo accounts share the password `Password123!`.
- `npm run seed:complaints` — ~60 synthetic complaints across every category, several
  incident clusters (2-12 complaints each, spanning every duplicate-count priority
  bracket), forced SLA breaches, resolved complaints with feedback. Uses the real
  priority/routing/SLA services for internal consistency but does not call OpenAI
  repeatedly (see the README's Limitations section).
